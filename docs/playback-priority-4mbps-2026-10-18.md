# 4 Mbps 播放优先优化（2026-10-18）

用户决定暂不升级公网带宽，当前只有一人使用。本轮保持 4 Mbps，优先当前播放、拖动恢复和减少重复流量。

## 实现

- 停止自动启动当前集整段预取和下一集预热队列；暂停也不再自动下载到片尾。
- 由 HLS 自身维护有限前向缓冲：开启缓存时基础目标 60 秒、上限 120 秒、30 MB 预算。边界可能多一个分片。
- 低缓冲时保留当前分片和紧邻下一片的有限重叠下载；拖到远处会取消旧位置的预加载。
- 完整 VOD TS 分片交给 HLS 解码前，保存已下载的字节到现有本机缓存，无额外网络请求。重新加载页面后也可复用。
- 仅完整、同源代理的 TS 分片进入该缓存路径；排除直播、低延迟分段、BYTERANGE、初始化数据与密钥。保留实际下载耗时及原剧集元数据，遵守缓存开关与 LRU 配额。
- 在 HLS 将 ArrayBuffer 转移到 Worker 前同步复制；单片最多 8 MiB，待写入总量最多 16 MiB。存储失败不阻断播放，切集时取消尚未开始的写入。
- 上一集/下一集、倍速、定时与家庭同步保持原有接口；没有新增离线功能。

## 验证

- 独立 Linux 源码快照：479 项测试通过，lint/typecheck/正式构建通过。
- 新增测试覆盖 Worker 转移导致的 buffer detach、缓存开关、重复写入、内存上限、剧集销毁以及存储失败。
- 生产版本 `playback-first-20261018`。登录、家庭数据只读访问、16 个源配置摘要、1,257,720 字节测试分片长度和 SHA256 均通过。
- 当前版本与 `transport-20261018` 回滚版本保留，临时构建和更早版本已清理，服务器剩余约 2.2 GiB。家庭数据和其他服务未修改。

## Chrome 方法

固定庆余年第一季第 11 集，1 倍速，原 LibreTV 观看标签暂回首页，使用独立标签。真实鼠标拖动进度条；测试前确认目标不在 MSE 缓冲区。临时忽略测试前的 TS CacheStorage 条目并禁用 HTTP 缓存，但允许本轮新写入的分片被复用；没有删除用户缓存。记录 seeking/playing/waiting、下载优先级、Resource Timing 和真实缓存写入。

原版对照来自同日上一轮：30:00 冷恢复 4.04 秒、后续 96 秒无额外等待；12:00 冷恢复 1.81 秒、再等待 1.71 秒。公网波动明显，因此不把单次时差当作严格性能提升比例。

## 实测结果

- 冷拖动 30:00.49：3.200 秒首次恢复；再等待 1.039 秒一次，之后 84.60 秒无额外等待。
- 本轮 30:00 记录 95.72 秒：54 次 TS 请求，额外后台 TS 请求 0，重复 URL 请求 0；53 个完整分片成功写入现有本机缓存。上一轮 111.68 秒记录包含 20 次后台 TS 请求，20 次重复 URL 请求。观察窗口不同，不将其换算为精确提速百分比。
- 冷拖动 12:00.13：3.600 秒恢复；之后 99.55 秒无再次等待。TS 请求 57 次，后台请求 0，重复请求 0，成功写入 58 个分片。
- 重载页面后回拖 30:00.49：0.0264 秒恢复。目标不在新的 MSE 缓冲区，命中持久缓存，记录期间新的代理/视频分片网络请求为 0。
- 暖缓存回拖后暂停观察 33.73 秒，未产生新的代理请求；当前位置前方连续缓冲 121.26 秒，未自动铺满整集或预热下一集。

冷拖动仍受 4 Mbps 和公网抖动限制，不能保证秒开或永不卡顿；本轮验证的确定改善是消除额外自动后台队列和重复请求，并使播放中下载的分片可以跨页面重载复用。
